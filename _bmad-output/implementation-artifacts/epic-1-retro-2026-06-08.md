## Significant Discovery: Woolworths API Architecture

**Finding:** Woolworths uses session/cookie-based authentication (not token-based), fundamentally different from Foodstuffs' Bearer token model.

**Evidence from existing code (`server/services/woolworths.ts`):**
- Foodstuffs: `POST /api/user/get-current-user` → `access_token` → Bearer auth
- Woolworths: `POST /api/v1/session` → cookie jar → session-based requests

**Decision: Scheme C — Unified `IStoreClient` interface with internal auth management**

- `IStoreClient.SearchAsync(term)` → `PriceResult[]` is the common contract
- Foodstuffs clients use `CachedTokenProvider` (3-layer: static → DB → API)
- Woolworths client manages session lifecycle internally (no `ITokenProvider`)
- `store_tokens` table serves Foodstuffs only

**Impact on Epic 2:**
- Story 2.1: `CachedTokenProvider` scoped to Foodstuffs only
- Story 2.2 & 2.3: Standard token-based auth via `CachedTokenProvider`
- Story 2.4: Independent session management, does NOT depend on Story 2.1
- Story 2.5: Unaffected — graceful degradation at `IStoreClient` level
